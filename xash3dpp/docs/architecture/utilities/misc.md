## Atlas packer (atlas.hpp / atlas.cpp)

The atlas packer allocates rectangular blocks within a fixed 2-D atlas using
a **strip-based bin-packing algorithm** (also called "shelf packing"):
each row of pixels is tracked by a single height value. A new block is placed
in the first column where enough vertical space exists.

### Constants

```cpp
static constexpr int ATLAS_MAX_SIZE = 1024;
```

The atlas is always a 1024×1024 grid. **This value is ABI-frozen** — changing
it breaks serialised atlas coordinates stored in BSP lightmaps and sprite
sheets. Do not change `ATLAS_MAX_SIZE` without a coordinated update to all
consumers.

### Block allocation

```cpp
struct Block { int x, y; };

std::optional<Block> alloc( int w, int h ) noexcept;
```

Attempts to place a `w × h` rectangle in the atlas. Returns `std::nullopt`
when the atlas is full or the rectangle is too large to fit. The returned
`Block{x, y}` gives the top-left corner of the allocated area.

Internally, `m_allocated[ATLAS_MAX_SIZE]` stores the current height (the
occupied Y extent) for each column. `alloc` scans for a run of `w` consecutive
columns that all have at most `ATLAS_MAX_SIZE - h` pixels used.

### Accessors

```cpp
int  max_height() const noexcept;   // current high-water mark across all columns
void reset() noexcept;               // clear all allocations
```

`max_height` is used by diagnostic code and renderer tests to monitor atlas
utilisation without re-scanning the full column array.

### No heap allocation

`Atlas` stores `m_allocated` as a `std::array<int, ATLAS_MAX_SIZE>` member,
not a pointer. The object can live on the stack or as a member of another
struct. There is no constructor allocation.

## Build metadata (build.hpp / build.cpp)

Namespace: `xash::utilities::build`

### Build number

```cpp
int  number() noexcept;
int  number_from_date( std::string_view iso_date ) noexcept;
```

`number()` returns the number of days elapsed since 2015-04-01 (the xash3d
project epoch). This value is used in the network protocol and engine banner.

`number_from_date` takes a `"YYYY-MM-DD"` string and computes the same
day-count. It is called internally by `number()` with the compile-time
`__DATE__` string, and is also exposed so tests can verify the calculation.

### Compatibility constant

```cpp
static constexpr int COMPAT_NUMBER = 4529;
```

The frozen build number that the legacy xash3d engine reported. Protocol code
that checks the remote build number may compare against `COMPAT_NUMBER` to
detect legacy clients and apply compatibility shims. **Do not change this
value.**

### VCS metadata

```cpp
extern const std::string_view commit;       // e.g. "abc1234"
extern const std::string_view branch;       // e.g. "master"
extern const std::string_view commit_date;  // e.g. "2024-11-03"
```

These symbols are declared `[[gnu::weak]]` so that link succeeds when
`build_vcs.cpp` (generated by the CMake configure step) is absent (e.g., in a
plain source tree without a VCS checkout). The weak-symbol fallback values are
`"(unknown)"` and `"1970-01-01"`.

When `build_vcs.cpp` is present and linked, it provides the actual commit hash,
branch name, and commit date from the VCS system at configure time.

## DLL export helpers (dynlib.hpp / dynlib.cpp)

Plugin loaders (renderer, filesystem, client, server) use a table-driven
approach to resolve exported symbols from shared libraries.

```cpp
struct ExportEntry {
    const char  *name;   // exported symbol name (must not be null)
    void       **slot;   // pointer to the function-pointer slot to fill
};
```

### `clear_exports`

```cpp
void clear_exports( std::span<ExportEntry> entries ) noexcept;
```

Sets every `*slot` to `nullptr`. Called before library unload so that no
dangling function pointers remain.

### `validate_exports`

```cpp
bool validate_exports( std::span<const ExportEntry> entries ) noexcept;
```

Returns `true` if every `*slot` is non-null. Called after `GetProcAddress` /
`dlsym` resolution to confirm that all required exports were found.

Typical usage:

```cpp
void *render_draw_scene_ptr = nullptr;
void *render_end_frame_ptr  = nullptr;

ExportEntry renderer_exports[] = {
    { "RenderDrawScene", &render_draw_scene_ptr },
    { "RenderEndFrame",  &render_end_frame_ptr  },
};

clear_exports( renderer_exports );
// ... resolve via GetProcAddress / dlsym ...
if ( !validate_exports( renderer_exports ) )
    host_error( "renderer DLL is missing required exports" );
```

Legacy: `COM_CheckParm`-style manual checks scattered throughout `ref/` and
`engine/`.

## GameInfo parser (gameinfo_parser.hpp / gameinfo_parser.cpp)

Namespace: `xash` (not `xash::utilities`)

Depends on `xash3dpp/gameinfo.hpp` for the `GameInfo` struct.

### Current status: stubs

All parsing and serialisation functions are **stubs** that return
`std::nullopt` or an empty string. They are compile-time placeholders;
the real implementation is a TODO. Only `apply_gameinfo_fixups` contains
working logic.

### API

```cpp
// Parse a gameinfo.txt file (GoldSrc format).
// Returns nullopt if the text is empty or malformed.
std::optional<GameInfo> parse_gameinfo_txt( std::string_view text ) noexcept;

// Parse a liblist.gam file (Half-Life 1 / legacy format).
// Returns nullopt if the text is empty or malformed.
std::optional<GameInfo> parse_liblist_gam( std::string_view text ) noexcept;

// Serialise a GameInfo to a gameinfo.txt string.
// Returns an empty string (stub).
std::string serialise_gameinfo( const GameInfo &info );

// Apply post-parse fixups: clamp budget fields to safe ranges.
// This is the only function with a real implementation.
void apply_gameinfo_fixups( GameInfo &info ) noexcept;
```

### `apply_gameinfo_fixups`

Clamps `GameInfo` budget fields to prevent excessive memory pre-allocation from
a malformed or hostile gameinfo.txt:

| Field | Minimum | Maximum |
|-------|---------|---------|
| `max_edicts` | 600 | 8192 |
| `max_tents` | 64 | 4096 |
| `max_beams` | 64 | 512 |
| `max_particles` | 1024 | 131072 |

These limits mirror the clamping logic in the legacy `filesystem.c`
`FS_ParseGameInfo` function.

### Namespace placement

`gameinfo_parser.hpp` lives in namespace `xash`, not `xash::utilities`, for
two reasons:
1. It depends on `xash::GameInfo` (from `xash3dpp/gameinfo.hpp`), which is a
   package-root type, not a utilities-scoped type.
2. `GameInfo` is used across multiple subsystems (filesystem, host, client);
   tying the parser to the `utilities` sub-namespace would create an awkward
   reference (`xash::utilities::parse_gameinfo_txt` → `xash::GameInfo`).
